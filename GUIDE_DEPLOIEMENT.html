Tableau de bord « Fréquentation des gares »

Guide de déploiement sur un serveur Windows ou Linux sans accès Internet, avec les validations lues dans SQL Server.

En bref. Le tableau de bord est une application Streamlit (un outil Python qui affiche une page web). Il lit les validations de Validations_load_30mn, la liste des gares de Ref_Gares et les prévisions de validations_horaires_forecast. Les postes de l'entreprise l'ouvrent dans leur navigateur, à l'adresse http://NOM_DU_SERVEUR:8501. L'installation se fait en 5 étapes : la première sur un PC qui a Internet, les autres sur le serveur.

Avant de commencer

Anaconda, sur le PC et sur le serveur
Les scripts utilisent le Python d'Anaconda (la distribution Python installée sur les deux machines). Ils le cherchent tout seuls aux emplacements habituels (C:\ProgramData\anaconda3, C:\Users\…\anaconda3, C:\anaconda3…). S'il est ailleurs, écrire son dossier (celui qui contient python.exe) dans outils\chemin_anaconda.txt. Sur le serveur, l'étape 2 y enregistre le dossier trouvé : le démarrage automatique, qui tourne avec le compte Windows SYSTEM, en a besoin. L'application s'installe dans son propre environnement (.venv) : l'environnement de base d'Anaconda n'est pas modifié. Pour connaître la version de Python du serveur : python --version dans « Anaconda Prompt ».
Sur le serveur : le pilote ODBC pour SQL Server
Le pilote ODBC est le composant Windows qui permet à un programme de dialoguer avec SQL Server. Il est sans doute déjà là si des traitements Python tournent sur ce serveur. Pour le vérifier : menu Démarrer, « Sources de données ODBC (64 bits) », onglet Pilotes : chercher ODBC Driver 17 for SQL Server (ou 18). Sinon, télécharger « Microsoft ODBC Driver for SQL Server » depuis le PC qui a Internet et l'installer.
Un compte SQL Server en lecture
Un identifiant et un mot de passe SQL qui peuvent lire les trois tables. Un compte réservé au tableau de bord, en lecture seule, est préférable.
Le port 8501 joignable depuis les postes
Un port est le numéro de « porte » réseau sur laquelle le tableau de bord répond. L'étape 5 l'ouvre dans le pare-feu Windows du serveur ; si un pare-feu réseau sépare les postes du serveur, demander son ouverture à l'équipe réseau.

Les 5 étapes

1

Préparer le paquet PC avec Internet

Sur un PC Windows qui a Internet et Anaconda, double-cliquer sur scripts\1_preparer_sur_un_pc_avec_internet.bat. Le script demande la version de Python du serveur (par exemple 3.12), puis télécharge :

  • les paquets Python (les bibliothèques dont l'application a besoin) dans le dossier paquets\ ;
  • la police de caractères et la bibliothèque de carte dans le dossier static\, pour que l'affichage ne dépende pas d'Internet.

Derrière un proxy d'entreprise (un intermédiaire obligatoire vers Internet), taper d'abord set HTTPS_PROXY=http://adresse-du-proxy:port dans l'invite de commandes, puis lancer le script depuis cette même fenêtre.

2

Installer sur le serveur Serveur

Copier tout le dossier sur le serveur, par exemple dans D:\Applications\frequentation_gares, puis double-cliquer sur scripts\2_installer_sur_le_serveur.bat. Le script :

  1. crée l'environnement Python .venv : un dossier qui contient les paquets de l'application, isolé du reste du serveur ;
  2. installe les paquets depuis paquets\, sans Internet ;
  3. crée .streamlit\secrets.toml et l'ouvre dans le Bloc-notes : y saisir les identifiants des deux serveurs SQL (section [sqlserver] pour les validations, section [sqlserver_previsions] pour les prévisions), enregistrer, fermer ;
  4. lance la vérification (voir étape 3).
secrets.toml contient un mot de passe : ne jamais l'envoyer par mail ni le copier ailleurs.
3

Adapter les requêtes SQL, puis vérifier Serveur

Le dossier sql\ contient trois requêtes qui décrivent les tables. C'est le seul endroit où figurent des noms de colonnes : les lignes marquées -- À ADAPTER sont des exemples à remplacer par les vrais noms.

FichierColonnes à renvoyer (avec exactement ces noms, grâce à AS)
1_validations.sqldate_heure (date et heure de la validation), gare (nom de la gare), sens ('E' entrée ou 'S' sortie), nb (1 par validation). Ne garder que les validations à l'état « ok ».
2_previsions.sqldate_heure (début de l'heure prévue), gare, sens, nb (nombre prévu) ; facultatif : nb_bas et nb_haut pour dessiner une bande d'incertitude autour de la courbe.
3_gares.sqlgare ; facultatif : ordre (position sur la ligne), zone, latitude, longitude.

Pour voir les colonnes réelles des tables :

.venv\Scripts\python.exe verifier_installation.py --colonnes

Après chaque correction, relancer la vérification. Elle contrôle la connexion, puis chaque requête (colonnes, entrées et sorties bien distinguées, gares inconnues, durée, couverture des prévisions) et dit précisément quoi corriger :

.venv\Scripts\python.exe verifier_installation.py
Astuce : chaque requête se teste aussi telle quelle dans SSMS (ajouter TOP 100 après SELECT). Deux règles pour les fichiers 1 et 2 : une seule instruction SELECT, sans ORDER BY ; et pas de filtre sur les dates, l'application l'ajoute elle-même.
4

Essayer Serveur

Double-cliquer sur scripts\3_lancer.bat, puis ouvrir http://localhost:8501 sur le serveur, ou http://NOM_DU_SERVEUR:8501 depuis un poste. Fermer la fenêtre noire arrête le tableau de bord.

5

Mettre en service Serveur

Clic droit sur scripts\4_demarrage_automatique.bat, puis Exécuter en tant qu'administrateur. Le script :

  • crée la tâche planifiée « Frequentation des gares » (un programme lancé automatiquement par Windows) : le tableau de bord démarre avec le serveur, tourne en arrière-plan et repart tout seul s'il s'arrête ;
  • ouvre le port 8501 dans le pare-feu Windows (le filtre qui autorise ou bloque les connexions réseau) ;
  • démarre le tableau de bord. Son journal (la trace de son fonctionnement) est dans logs\streamlit.log.

Pour l'arrêter : scripts\5_arreter.bat (en administrateur). Pour supprimer la tâche : schtasks /delete /tn "Frequentation des gares" /f.

Sur un serveur Linux

Même principe, avec les scripts du dossier scripts_linux/ (à lancer dans un terminal). Différences avec Windows :

Le pilote Microsoft ODBC pour SQL Server et unixODBC (la couche ODBC de Linux) doivent être installés par l'administrateur du serveur : paquets msodbcsql18 et unixODBC, téléchargés depuis le site de Microsoft sur une machine qui a Internet. Dans secrets.toml, écrire alors pilote = 'ODBC Driver 18 for SQL Server'.

Mettre en servicesudo bash scripts_linux/4_demarrage_automatique.sh : crée le service systemd frequentation-gares (l'équivalent Linux de la tâche planifiée : démarrage avec le serveur, relance automatique) et ouvre le port 8501 dans le pare-feu (firewalld ou ufw). Réglages courants : parametres.toml

Ce fichier s'ouvre avec le Bloc-notes. Après une modification, recharger la page dans le navigateur (touche F5).

RéglageRôle
mode"reel" : vraies données SQL Server. "demo" : chiffres simulés, sans base, pour tester l'affichage.
afficher_pages_simuleesAffiche les pages « Suivi des trains » et « Serpent de charge » (horaires GTFS théoriques, retards simulés : ce n'est pas du GTFS-Realtime). L'écran TV n'est plus proposé.

GTFS théorique et simulation des trains

La requête sql/4_gtfs_horaires.sql lit les services actifs dans calendar, les circulations dans trip, les lignes dans route, les arrêts et horaires dans stop et stop_time. Les pages Suivi, Serpent de charge et Écran TV sont activées. Les positions et retards sont simulés à partir des horaires ; aucune source GPS ou GTFS-RT n'est branchée.

Si les tables GTFS sont sur un autre serveur, ajouter la section [sqlserver_gtfs] dans .streamlit/secrets.toml (un exemple figure dans .streamlit/secrets.toml.exemple). Adapter les noms de colonnes dans sql/4_gtfs_horaires.sql si le schéma importé diffère du standard GTFS.

Comment les chiffres sont calculés

  • Heure de référence : les validations arrivent par lots toutes les 30 minutes. Les indicateurs de fréquentation sont donc calculés jusqu'à la dernière validation reçue, affichée dans l'en-tête ; les comparaisons « à la même heure » se font à cette heure-là.
  • vs. hier à la même heure : cumul d'aujourd'hui comparé au cumul d'hier arrêté à la même heure.
  • vs. semaine habituelle : passages des 60 dernières minutes, comparés aux mêmes 60 minutes des mêmes jours, les 4 semaines précédentes (une semaine sans aucune donnée est écartée de la moyenne).
  • Affluence habituelle : moyenne par jour de la semaine et par heure sur les 4 dernières semaines.
  • JOJ : réel pour les jours terminés ; pour aujourd'hui, réel jusqu'à la dernière validation plus la prévision du reste de la journée ; ensuite, la prévision. La « période normale » est la moyenne, par jour de la semaine, des 4 semaines avant les Jeux.
  • Prévision : les valeurs de validations_horaires_forecast, telles quelles.
  • Aucun chiffre inventé : en mode réel, si une donnée ne peut pas être lue, le bloc concerné affiche l'erreur exacte au lieu de chiffres simulés.

En cas de problème

Ce que l'on voitCause probableSolution
Installation : « No matching distribution found »La version de Python choisie à l'étape 1 n'est pas celle du serveur. Relancer l'étape 1 avec la bonne version (python --version sur le serveur), recopier paquets\, relancer l'étape 2.
« Anaconda introuvable »Anaconda est installé dans un dossier inhabituel. Écrire son dossier (celui qui contient python.exe) dans outils\chemin_anaconda.txt.
« DLL load failed » au lancementComposants Microsoft Visual C++ absents du serveur. Installer « Microsoft Visual C++ Redistributable » x64 (téléchargé depuis le PC qui a Internet).
« Connexion à SQL Server impossible »Nom du serveur, identifiants ou pilote incorrects ; réseau fermé entre les deux serveurs. Corriger .streamlit\secrets.toml ; le message affiche la liste des pilotes présents.
« Invalid column name … »Un nom de colonne d'exemple n'a pas été adapté. Corriger le fichier du dossier sql\ indiqué, à l'aide de verifier_installation.py --colonnes.
En-tête orange « Données en retard »Plus aucune validation n'arrive : le chargement toutes les 30 min (job_validations_sales_30mn) est arrêté ou en échec. Vérifier ce traitement ; le tableau de bord reprend tout seul dès l'arrivée de nouvelles validations.
« Aucune prévision »La table des prévisions ne couvre pas les prochaines 24 heures. Vérifier la dernière exécution du modèle de prévision et sql\2_previsions.sql.
Toutes les entrées, aucune sortie (ou l'inverse)La valeur qui désigne une sortie (ou une entrée) n'est pas la bonne dans le CASE. Corriger les valeurs 'entree' / 'sortie' dans sql\1_validations.sql.
Page lentePas d'index (une table de recherche qui évite de relire toute la table) sur la colonne date-heure des validations. Demander un index sur cette colonne à l'administrateur de la base.
Page injoignable depuis les postesTâche arrêtée, ou port 8501 bloqué par un pare-feu. Ouvrir http://localhost:8501 sur le serveur ; lire logs\streamlit.log ; faire ouvrir le port côté réseau.

Mettre à jour l'application

  1. Arrêter : scripts\5_arreter.bat (en administrateur).
  2. Remplacer les fichiers de l'application, en gardant .streamlit\secrets.toml, parametres.toml et le dossier sql\.
  3. Redémarrer : schtasks /run /tn "Frequentation des gares" (ou redémarrer le serveur).

Contenu du dossier

app.py — l'application (pages et affichage)
donnees.py — lecture des données : SQL Server (mode réel) ou chiffres simulés (mode démonstration)
parametres.py — lecture des réglages
parametres.toml — les réglages (mode, horaires, JOJ, zones)
verifier_installation.py — vérification de la connexion et des requêtes
requirements.txt — liste des paquets Python
sql\ — les trois requêtes qui décrivent les tables (à adapter)
.streamlit\config.toml — réglages du serveur web (port 8501, thème)
.streamlit\secrets.toml.exemple — modèle du fichier des identifiants SQL Server
scripts\ — les 5 étapes de l'installation
outils\ — utilitaires appelés par les scripts (tâche planifiée, téléchargements, relance automatique)
assets\ — logos et images
static\ — police et carte, remplis par l'étape 1
scripts_linux/ — les mêmes étapes pour un serveur Linux
paquets\, paquets_linux/, .venv\, logs\ — créés pendant l'installation
